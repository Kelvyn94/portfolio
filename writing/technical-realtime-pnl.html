Real-Time P&L Without a Complicated Backend

~800 words · Technical

"Real-time" in a trading journal's UI sounds like it demands a streaming architecture — websockets, a message queue, a service dedicated to fanning out price ticks to connected clients. For a single-user or small-scale journal application, most of that is unnecessary weight solving a problem the actual usage pattern doesn't have.

What "real-time" actually needs to mean

A trader glancing at an open position wants a P&L figure that's close enough to current price to be trustworthy — not a figure that's provably synchronized to the millisecond with an exchange feed. That distinction matters because it changes the engineering budget entirely: a figure refreshed every few seconds via polling is indistinguishable, to a human looking at a screen, from one pushed instantly via a websocket, as long as the polling interval is short enough relative to how fast the instrument actually moves. For forex and metals — the instruments Tradex is built around — a price fetched every three to five seconds is more than sufficient for a journal's display purposes; it is not sufficient for algorithmic execution, but a journal isn't executing trades, it's displaying context for a human.

Where the computation should live

The trade record itself — entry price, size, direction — is static once a trade is open; it doesn't need to be rewritten every time price moves. Current price is the only volatile input, and it's fetched and cached independently, on its own short polling interval. P&L is then computed client-side, on demand, from the static trade data plus the last cached price — a simple multiplication, not a database write. This keeps the database's write pattern boring and predictable (a trade row is written at entry, occasionally amended, and once more at close) while the "live" feeling in the UI comes entirely from the price cache refreshing and the client recomputing the display value locally.

The alternative — writing an updated P&L value to the trade record on every price tick — sounds more "real" but is strictly worse: it multiplies database writes by however many open positions and price updates are happening, for a value that's derivable from data already in the row. It also creates a subtle correctness risk, since a stored, periodically-updated P&L value can silently go stale if a write is missed, whereas a value computed fresh on every render can't be stale by definition — it's only ever as old as the last price fetch.

Where this approach stops being sufficient

This is a deliberate trade-off, not a universal rule. It holds for a single-user or small-team journal displaying P&L to a human. It stops holding the moment the use case shifts to something that genuinely needs sub-second synchronization across many concurrent clients watching the same data — a multi-user dashboard, or anything feeding an automated decision downstream. Recognizing that boundary is the actual skill here: reaching for websockets and a pub/sub layer by default, before the usage pattern actually demands it, adds operational surface area — more moving parts to deploy, monitor, and debug — that a polling-plus-client-side-computation approach avoids entirely for the cases where it's genuinely sufficient.

The general principle

"Real-time" is a UX requirement, not automatically an infrastructure requirement. The right question isn't "how do I make this real-time" — it's "how close to current does this actually need to be, for whom, and what's the cheapest architecture that hits that bar." For a trading journal's open-position display, the answer was a short polling interval and client-side computation, and it produced a UI that feels live without any of the operational cost of a streaming stack that the actual usage pattern never needed.
